## Verdict

**The mapping feature got built, and the module works.** Every headline finding from round 1 is
fixed. An analyzer code binds to a real catalog test through the GUI, from the whole 183-test
catalog, with LOINC shown. The profile no longer applies partially and silently — unresolved codes
carry an explicit `mappingState` and can be mapped or excluded. The sign-off is a recorded artefact
with a signer and a timestamp, pinned to a `bindingFingerprint` *and* a `recognitionFingerprint`, so
it goes stale when either changes. QC is no longer coupled to activation. And the analyzer lifecycle
runs end to end: activate → deactivate → reactivate, from the API and from the UI, with no hard
Delete anywhere. **Twelve of thirteen round-1 findings closed.**

**Nothing here is a blocker.** What remains is one carried-over defect that should have been fixed
this round and is now worse rather than better (Δ-R — operational QC cannot be configured at all),
one design gap that may be a spec question (Δ-K), one data-integrity bug worth fixing before a lab
meets it (Δ-S), one dead end in the "my instrument isn't listed" path (Δ-Y), and two small ones
(Δ-V, Δ-W).

**Maturity: M3.** Instrument, the mapping editor and the lifecycle all round-trip through a second
surface, and the mapping cross-links to the real test catalog. REPORTABLE is not evidenced — but
only because result ingestion needs the analyzer simulator, which this instance does not have.
Standing up that simulator is now the highest-value next step for this module, because it is the
only thing between OGC-1057 and a reportable grade.

**Recommendation: mergeable.** Δ-R and Δ-S are worth landing first; neither blocks the others.

## A finding this report withdraws — please read before acting on the review submission

The in-app review (**submission id 16**) records **step 5 "Activate the analyzer" as Fail**, and an
earlier draft of this report led with a blocker: *"`activation-readiness` returns `ready:true` while
`POST /activate` returns 500, deterministically, reproduced on a second analyzer."*

**That finding is wrong and is withdrawn.** It came from hand-rolled `POST`s during the interactive
walkthrough that omitted this build's CSRF header. Every non-GET REST call on 3.2.2.0 must carry
`X-CSRF-Token`, whose value lives in `localStorage.CSRF`; without it the server answers
`403 {"message":"CSRF token missing or invalid"}`.

With the header, on analyzers **363** and **364**, repeatedly and in both directions:

```
POST /rest/analyzer/analyzers/363/activate    → 200  {"status":"ACTIVE","activated":true,"blockers":[]}
POST /rest/analyzer/analyzers/363/deactivate  → 200  {"status":"INACTIVE","deactivated":true}
POST /rest/analyzer/analyzers/363/reactivate  → 200  {"status":"ACTIVE","activated":true}
```

The UI agrees. *Connect → Finish and activate* issues `PUT …/364` **200** then
`POST …/364/activate` **200**, and the row flips to **Active**. The row menu's *Deactivate* returns
**200** and the row flips to **Inactive**; *Reactivate* — offered only on inactive rows — returns
**200** and it flips back. All four paths are now guarded by tests that pass.

**Δ-U ("reactivate is untestable") is withdrawn with it.** Reactivate works.

Two honest caveats. First, a request without the header returns 403, not 500, so the 500s the
walkthrough saw are not fully explained by the missing header alone — either the build changed under
us between ~16:20 and ~18:15 UTC, or the probe was malformed in a second way. Second, the UI banners
observed at the time (*"Deactivation failed — Internal Server Error"*, *"Analyzer readiness could not
be checked"*) were real observations that no longer reproduce. **Either way the defect does not
reproduce and should not be filed.** If anyone has already started on it, stop.

The lasting lesson is a harness rule, now recorded in the QA repo: *a write that omits CSRF does not
merely fail — it manufactures a finding.*

## Δ ledger

### Δ-R — the New Control Lot form cannot be saved at all **(revised — this is not what round 1 found)**

Round 1 reported this as *hidden validation*: the form POSTed, the server answered
`400 "Manufacturer fixed method requires both mean and standard deviation"`, and the banner said
only *"Failed to save control lot"*. **On 3.2.2.0 that is no longer the defect.** The form now
issues **no request at all**, so there is nothing for the UI to surface and setting Mean/SD changes
nothing. The finding is an **unwired Save**, not a validation-messaging problem — the earlier
framing in this report and in the in-app review has been corrected accordingly.

**Observed.** With every field populated — lot number, control material, control level, expiration
date, analyzer, test, Active, and Mean 25.00 / SD 2.50 set through *Statistics Configuration* —
clicking **Save**:
- issues **no network request** (verified with the browser's own network recorder),
- logs **no console error or exception**,
- marks **no field invalid** and shows **no message**,
- does not navigate, and
- leaves `GET /rest/qc/control-lots` returning `[]` — "No control lots found".

**The handler is wired but bails.** Save is `type="submit"`, enabled, inside a real `<form>` that
carries a React `onSubmit` function. So the submit path exists and returns before issuing anything.

**Endpoint probe.**
```
GET  /rest/qc/control-lots  → 200  []                       ← list endpoint, works
POST /rest/qc/control-lots  → 405  Method Not Supported     ← no create handler at this path
POST /rest/qc/controlLot    → 400  (exists, different DTO)
```
The list and the create endpoints live at different paths (`/qc/control-lots` vs `/qc/controlLot`),
which may be part of why nothing is wired up.

**Revalidation** (per the QA repo's bug-revalidation protocol):
- **Method A — fresh tab: CONFIRMED.** New tab, fresh login (new session id and CSRF), navigated by
  **sidebar** (Analyzers → Quality Control → Control Lots) and entered through the canonical
  **New Control Lot** button rather than a direct URL, all interaction by real mouse click.
- **Method B — full re-login: CONFIRMED.** That run began at `/login` in a clean session.
- **Method C — endpoint probe:** as above.
- **Tooling ruled out:** the network recorder captured `GET /rest/qc/control-lots → 200` on the same
  tab moments later, so "zero requests on Save" is a real observation, not a capture gap.
- Reproduced across two tabs, two sessions, two entry paths, two analyzer/test combinations, with
  and without Mean/SD, and via synthetic click, real mouse click and Enter-key submit.

**Consequence.** Operational QC cannot be configured at all: control lots cannot be created, and
**Rule Configuration has no create control** ("No rule configurations found", nothing to add one).
The **QC Dashboard also reports "No instruments found"** while the Analyzers list holds 10 analyzers
with one ACTIVE — so the QC area appears disconnected from the analyzer inventory generally.

Severity: **High.** It is not a release blocker — activation deliberately does not depend on QC
(see AC-9) — but a lab cannot run quality control, and it is the second round in a row this surface
has shipped broken.

### Δ-S — Add Analyzer does not reset the setup panel
With an analyzer open (row menu → *Edit setup*), clicking **Add Analyzer** drops `analyzerId` from
the URL — the panel looks fresh — but retains the previous analyzer's values *and its identity*.
Continue then issues `PUT /rest/analyzer/analyzers/{previous id}` and silently renames it. From a
clean list page, Add works correctly (`POST` → 201). Data-integrity risk in the exact scenario a lab
hits: adding a second, identical instrument right after inspecting the first.

### Δ-K — no data-flow control
The connection block is a declarative field schema, and its fields are `transport`
(Serial RS-232 / Network TCP/IP), `connectionRole` (Server / Client), `host` and `port` — **there is
no `dataFlow` field**. That is who opens the socket and over what, not FR-F's *Results only
(one-way)* versus *Two-way (send orders/queries)*, so AC-10 cannot be satisfied as written.

**This may be a spec question rather than a build gap.** If data flow is now derived from the
protocol by Analyzer Bridge, FR-F2 and AC-10 should say so and the requirement should be amended.
Worth a decision before anyone builds a control that duplicates what the Bridge already knows.

### Δ-Y — "my instrument isn't listed" reaches Create Profile, which is a dead end

The escape hatch exists (round 1's Δ-D is fixed) but cannot be completed. **Create Profile collects
only a name**, then reports *"Profile draft created — the draft is saved in Analyzer Bridge. It must
be completed and validated before it can be published for analyzer setup."* There is no editor, no
Publish action, and the draft never appears in the Analyzer Types list. Re-opening
`?action=create&draft={uuid}` shows the same terminal message.

The draft does exist server-side, and the server names exactly what a publishable profile needs:

```
POST /rest/analyzer-types/drafts/{id}/publish → 400
  "Profile draft cannot be published: $.profileMeta: required property 'confidence' not found;
   $.profileMeta: required property 'version' not found; $: required property 'capabilities'
   not found; $: required property 'category' not found; $: required property 'configDefaults'
   not found; $: required property 'connectionFields' not found; $: required property
   'controlResultRecognition' not found; ..."
```

So FR-B3's protocol and connection type do **not** appear downstream — they are required by the
Bridge contract and nothing in OpenELIS collects them. The backend is well specified and validates
properly; **this is a UI gap.** A deployment can currently only fork an existing type, never author
a new one.

### Duplicate Profile works, and it is the FR-H fork **(new — previously untested)**

Worth recording as the counterexample, because it shows what the create path is missing. The modal
states the semantics outright — *"New profile with preserved lineage. The new profile starts from
Cepheid GeneXpert (ASTM Mode) revision 1. Later changes do not alter the source profile or its
analyzers."* — then `POST /rest/analyzer-types/{id}/duplicate` → **201** opens a real draft editor
with the inherited control-recognition conditions editable, and
`POST /rest/analyzer-types/drafts/{id}/publish` → **201** publishes it. The result lands in the list
as *QA Fork GeneXpert FR-H · Site-created · Derived from genexpert-astm revision 1 · ASTM*, and the
source type's page shows an **"Update available"** badge against each analyzer using it. **FR-H is
satisfied.**

Minor: each profile action fires its POST **twice** on a single click (duplicate 2×, publish 2×).
The same `draftId` comes back both times, so it appears idempotent, but the double submit is worth
a look.

### Δ-V — both lifecycle dialogs render the literal `{name}` placeholder
> *"Deactivate {name}? New runtime use will stop. Its configuration and history will be retained,
> and it can be reactivated later."*
> *"Reactivate {name}? Its setup will be checked again before it can be used."*

Same defect class as the Delete-dialog placeholder bug (NOTE-22) — it moved with the rename rather
than being fixed, and it is now in two places. Cheap to repair, and it is the last thing a user
reads before a state-changing action.

### Δ-W — the pickers jump to a match but never narrow the list *(minor / UX)*
Both Carbon ComboBoxes accept text and neither filters: the analyzer-type picker holds its option
count at 3 for any query, the per-row test picker at **183 before and 183 after**. What they do
instead is jump to the match and highlight it, and that works on both a name prefix
(`Hemato` → *Hematocrit · Hematocrit-Blood · 4544-3*) and a LOINC
(`85362` → *Xpert MTB/RIF · 85362-2*) — so the placeholder's *"Search by name, code, or LOINC"* is
honest. The cost is that the menu never shrinks, so a user comparing candidates still scrolls 183
rows. Fix is one prop on the Carbon `ComboBox` (`shouldFilterItem`).

This is the narrow, real residue of two separate "there is no search" claims that were both
withdrawn — stated precisely here so it is not raised a third time.

### Minor
- The Port field shows "This field is required" while holding a value, until blurred.
- The analyzer-scoped QC page displayed "In Control" for an analyzer with no control lot.

## What works and should not be allowed to regress

The re-baselined suite guards these explicitly, with assertions that are *not* flip-when-fixed:

- Bound mapping rows resolve to a catalog test object, not a name hint; every code carries a
  `mappingState`; `controlRecognition` is present.
- The mapping is a versioned, fingerprinted **site binding**, so a lab's change never edits the
  shipped profile.
- The confirmation is pinned to both the binding and the recognition fingerprint — the mechanism
  that makes staling work at all.
- No QC blocker appears in `activation-readiness`.
- The connection schema drives field visibility from the server (`host` appears only when the role
  is `CLIENT`; `connectionRole` only when transport is not RS-232).
- The probe is real and its outcome is persisted against a `configRevision`.
- The row menu offers Deactivate/Reactivate and **no Delete**.

## Design questions for the PO (not defects)

- **Create Profile collects only a name.** The modal then reports *"Profile draft created — the
  draft is saved in Analyzer Bridge. It must be completed and validated before it can be published
  for analyzer setup."* FR-B3 specifies protocol and connection type at this point; on 3.2.2.0 they
  are defined outside OpenELIS. The path is reachable, but a lab admin cannot finish the job in this
  UI. Confirm the split is intended, and amend FR-B3 if so.
- **The analyzer-scoped QC link opens a monitoring view** (Activity Timeline / Control Chart).
  Control-lot and Westgard configuration live in the sidebar, so the QC step of setup cannot be
  completed from the analyzer link itself.

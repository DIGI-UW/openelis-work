## Verdict

**The mapping feature got built.** Every headline finding from round 1 is fixed. An analyzer code
can now be bound to a real catalog test through the GUI, from the whole 183-test catalog, with
LOINC shown; the profile no longer applies partially and silently — unresolved codes are explicit
and can be mapped or excluded; the sign-off is a real recorded artefact with a signer and a
timestamp that goes stale when a binding changes and gates Continue while it is stale; and QC is no
longer coupled to activation. Eleven of thirteen findings closed. That is a substantial build.

**What blocks it is now one defect, not twelve.** No analyzer can be activated, and none can be
deactivated. `GET …/activation-readiness` returns `{ready: true, blockers: []}` and `POST …/activate`
returns **500** on the same analyzer, deterministically, reproduced on a second analyzer created
fresh. Deactivate returns 500 as well. Because ACTIVE is unreachable, everything downstream of an
active analyzer — result ingestion, the QC program running against live data, anything the feature
exists to enable — cannot be exercised at all, by us or by a lab.

**Recommendation: not ready to merge as-is.** Δ-T alone is the gate. Fix it and the module is
plausibly M4 on the next look; the remaining four findings are narrow and none of them blocks
another. Round 1's report should be read as history from here.

**Maturity: M2.** Instrument and the mapping editor round-trip properly and would rate M3 on their
own. The module rates at its lowest sub-feature, and the lifecycle is M0.

## Δ ledger

### Δ-T — the analyzer lifecycle is broken in both directions **(blocker)**

Two server endpoints disagree about the same analyzer:

```
GET  /rest/analyzer/analyzers/363/activation-readiness → {"ready":true,"blockers":[]}
POST /rest/analyzer/analyzers/363/activate   body {}   → 500 Internal Server Error
POST /rest/analyzer/analyzers/363/deactivate body {}   → 500 Internal Server Error
```

Deterministic 3/3 on analyzer 363. **Reproduced on analyzer 364**, created fresh and brought to
ready with a deliberately *failed* connection test — so it is not a property of the seeded record.

The not-ready path is correct, which is the useful part of the diagnosis: before 364's port was
set, both endpoints returned a well-formed **422** with
`analyzer.connection.readiness.missingRequiredValues`, and earlier, with mappings unconfirmed,
activate returned 422 with `analyzer.activation.blocker.mappings` + `.recognition`. So readiness
evaluation is sound and the **transition** is what fails. Since activate and deactivate fail the
same way, they likely share one defect in the lifecycle service — plausibly the push to Analyzer
Bridge, as each analyzer carries `bridgeConnectionId`, `connected: true` and a
`connection.configRevision`. **Server logs for 2026-08-25 ~16:19–16:40 UTC will name it.**

Severity: **blocker**. Nothing downstream of an ACTIVE analyzer is reachable.

### Δ-U — reactivate is untestable
While deactivate 500s, nothing on the instance can be put into INACTIVE, so the reactivate path has
never been exercised on this build. Deferred, not judged. Re-test when Δ-T is fixed.

### Δ-V — the Deactivate dialog renders the literal `{name}` placeholder
The confirmation reads *"Deactivate {name}? New runtime use will stop…"*. Same defect class as the
Delete-dialog placeholder bug (NOTE-22) — it moved with the rename rather than being fixed. Cheap
to repair, and it is the last thing a user reads before a destructive-sounding action.

### Δ-K — no data-flow control (carried from round 1)
Connect offers **Transport** (Serial RS-232 / Network TCP/IP) and **Connection role** (Server /
Client) — who opens the socket. FR-F's choice is about what flows over it: *Results only (one-way)*
versus *Two-way (send orders/queries)*. That control still does not exist, so AC-10's "defaults to
one-way, two-way only where the profile declares it" cannot be satisfied. This may be a **spec
question as much as a build gap** — if data flow is now a property the Bridge derives from the
protocol, FR-F2 should say so and AC-10 should be rewritten.

### Δ-R — control-lot validation is still hidden (carried from round 1, unchanged)
```
POST /rest/qc/controlLot → 400  "Manufacturer fixed method requires both mean and standard deviation"
```
The banner shows only *"Failed to save control lot"*. Mean and SD live behind **Statistics
Configuration → Configure** and are not marked required. The server names the fields; the UI
discards that and tells the user nothing actionable. Reported 2026-08-12 and shipped again.

### Δ-S — Add Analyzer does not reset the setup panel
With an analyzer open (row menu → Edit setup), clicking **Add Analyzer** drops `analyzerId` from the
URL — the panel looks fresh — but retains the previous analyzer's values *and its identity*.
Continue then issues `PUT /rest/analyzer/analyzers/{previous id}` and silently renames it. From a
clean list page, Add works correctly (`POST` → 201). Data-integrity risk in the exact scenario a lab
hits: adding a second, identical instrument right after inspecting the first.

### Error surfacing is inconsistent
Deactivate reports its 500 properly. Activate shows only *"Analyzer readiness could not be
checked"* — which misattributes the failure, since readiness had just returned ready — and the 422
path shows nothing at all. Whoever fixes Δ-T should make the three paths agree.

### Minor
- The Port field shows "This field is required" while holding a value, until blurred.
- The analyzer-scoped QC page displayed "In Control" for an analyzer with no control lot.

## Withdrawn on evidence

- **"The instrument picker has no search."** Withdrawn twice, for two different reasons. Round 1: a
  harness artefact — synthetic keystrokes sent to an unfocused page were swallowed by a global
  search shortcut that navigated away and abandoned the setup. Round 2: option **count** was
  measured (183 before and after typing) and read as "no filtering", but this Carbon `Dropdown`
  **jumps to the match and highlights it** rather than filtering, and existing text must be cleared
  first. Typing `hem` highlights *Hematocrit · Hematocrit-Blood · 4544-3*. AC-3 is satisfied.
- **"Add Analyzer overwrites the analyzer you were looking at."** Withdrawn as stated — from a
  clean list, Add creates a new analyzer correctly. The real, narrower finding is **Δ-S**.

## Design questions for the PO (not defects)

- **Create Profile collects only a name.** The modal then reports *"Profile draft created — the
  draft is saved in Analyzer Bridge. It must be completed and validated before it can be published
  for analyzer setup."* FR-B3 specifies protocol and connection type at this point; on 3.2.2.0 they
  are defined outside OpenELIS. The path is reachable, but a lab admin cannot finish the job in this
  UI. Confirm the split is intended, and amend FR-B3 if so.
- **The analyzer-scoped QC link opens a monitoring view** (Activity Timeline / Control Chart).
  Control-lot and Westgard configuration live in the sidebar, so the QC step of setup cannot be
  completed from the analyzer link itself.

## Summary

The Inventory module has two related pieces of catalog-side tech debt: the **"Type of Item"** list is hard-coded with no admin management or localization, and the **inventory item primary key** is an opaque integer rather than a meaningful internal code. Both touch the same Inventory Catalog → Item Add / Edit form and share the "optional code, auto-generate, lock-on-save" pattern, so they ship together.

## User Stories

**As a** lab admin,
**I want** to manage the list of inventory item types from a dedicated admin page — adding new types, renaming for my locale, and deactivating ones I don't use,
**so that** the type list stays current as my lab's inventory needs change, without a code change or redeploy.

**As an** integrator (or admin reading reports / API responses),
**I want** every inventory item to have a stable, meaningful internal code as its primary key — auto-generated by default, optionally overridden in the GUI,
**so that** inventory references are human-readable, stable across deployments, and don't depend on opaque auto-increment IDs.

## Background

**Item Type list.** The "Type of Item" field on Inventory Catalog → Item Add is populated from a hard-coded list in source. Admins cannot rename for localization, deactivate, or add new types without a code change. We're moving this to a dedicated `inventory_item_type` table with a purpose-built admin CRUD at **Admin → General Configuration → Inventory**. Seeded types ship with translations baked in for all supported locales; admins adjust the name in their active locale only and can deactivate types they don't use.

**Inventory item primary key.** Inventory items today use an opaque auto-increment integer ID as the primary key. This story replaces that with a string `code` column as the PK — auto-generated server-side from the item name (e.g., `UPPER_SNAKE`) when not supplied, optionally overridden in the GUI. Lots and any other module referencing inventory items move from the integer FK to the string FK in the same release.

## Acceptance Criteria

### Part A — Inventory Item Type CRUD

A1. A new `inventory_item_type` table exists with `id`, `code` (stable string ID, used by integrations and other modules), `display_name` (canonical English fallback), `is_active`, `sort_order`, `is_seeded` (true for migration-seeded rows), and audit columns. Localized names use the existing OpenELIS localization mechanism (or a companion `inventory_item_type_localized_name` table if that's the prevailing pattern).

A2. A seed migration loads the current hard-coded item types as rows with `is_seeded = true`, with **translations pre-populated** for all supported deployment locales (English, French, Bahasa Indonesia at minimum).

A3. A new admin page lives at **Admin → General Configuration → Inventory** (sidenav submenu, not in-page tabs). The page is a `DataTable` listing item types with columns: Code, Name (in active locale), Status, Sort order, Actions.

A4. Admins can **add** a new item type via a primary "Add item type" button that opens an inline row at the top of the table. The Add form has: Code (optional, auto-generated `UPPER_SNAKE` from the name if blank), Name (saved as the translation in the admin's active locale), Sort order, Active toggle. No modal.

A5. Admins can **edit** an existing item type via inline row expansion (no modal). The edit form's Name field edits only the translation for the admin's **currently active locale**; the Code field is **disabled / locked** post-save with a hint explaining why; seeded translations for other locales are not exposed for editing in this UI.

A6. Admins can **deactivate** an item type. Deactivation is the only destructive action and uses a confirmation modal; the modal explicitly states that existing inventory items keep their assignment but the type stops appearing in the Item Add dropdown for new items.

A7. The **Inventory Catalog → Item Add** form loads the "Type of Item" select options from the new table, filtered to `is_active = true`, sorted by `sort_order`, and labels resolved through the existing localization mechanism. The hard-coded list in source is removed.

A8. A custom (non-seeded) type created by an admin saves the entered name as the translation in the admin's active locale; other locales fall back to the same value until separately translated. Seeded rows can be renamed for the active locale and deactivated, but not hard-deleted.

A9. The permission required to add / edit / deactivate inventory item types matches the permission already used for analogous admin-managed reference lists. No new permission key.

### Part C — Inventory item primary key migrated to internal code

C1. The inventory item entity uses a string `code` column as its primary key. The opaque auto-increment integer `id` is removed.

C2. The `code` value is generated server-side at item-create time from the item's name using the same `UPPER_SNAKE` convention used by item-type Code generation in Part A. If the resulting code collides with an existing code, a numeric suffix is appended (e.g., `REAGENT_KIT_2`).

C3. The **Inventory Catalog → Item Add** form has an **optional Code field** with the placeholder/hint "Leave blank to auto-generate from name". If the admin types a value, it is uppercased and validated for uniqueness; if blank, the server auto-generates per C2.

C4. Code is **locked once saved.** The Edit form displays the code as a read-only field with a hint explaining that integrations and existing references depend on it staying stable.

C5. The Inventory Catalog list / dashboard surfaces the `code` as a visible column (e.g., as the leftmost column or alongside the item name) so admins can see and search by code.

C6. **All FK references to inventory items elsewhere in the codebase** (lots, storage assignments, any reports / APIs / front-end views that resolve inventory items) move from the integer FK to the string `code` FK in the same release. No code path retains the legacy integer reference.

C7. A search on the Inventory dashboard matches against both the item name and the `code`.

C8. Validation on the Add form rejects codes that collide with an existing code, contain whitespace, or contain characters outside `[A-Z0-9_]`. The error message is i18n-keyed.

C9. Permissions for adding / editing inventory items are unchanged; no new permission key is introduced for the code field.

## Technical Notes

### Migration & breaking change

- Inventory has no external users yet; this is treated as a **clean break**.
- One Liquibase release contains: create `inventory_item_type` (with seed data + locale rows), remove the hard-coded item-type list from source, and migrate the inventory item PK from integer `id` to string `code` along with every FK referencing it.
- No migration of legacy data; pre-existing inventory item rows are dropped and recreated with auto-generated codes (or seed data is regenerated with the new schema).
- Release notes call out **both** breaking changes explicitly.

### Data model — Part A

- New `inventory_item_type` table per AC A1.
- Localization via the existing OpenELIS mechanism. **Confirm at implementation:** prefer reusing whatever pattern already powers other admin-managed localized reference lists rather than introducing a new approach.
- Seeded translations cover at minimum English, French, and Bahasa Indonesia.

### Data model — Part C

- Inventory item table's PK changes from integer `id` to string `code`. Column constraints: not null, unique, length cap (suggest 64 chars), character set `[A-Z0-9_]`.
- All tables that previously held an integer FK to inventory item (lots, any reports / cached views) move to the string FK in the same Liquibase changeset.
- Auto-generation logic lives server-side. Collision strategy: append `_2`, `_3`, … until unique.

### Front-end

- New admin CRUD page (Carbon `DataTable` + inline row expansion) at Admin → General Configuration → Inventory. Edit form bound to the active locale; modal reserved for deactivate confirmation only.
- Inventory Catalog → Item Add reads its type list from the new table via REST. The form gains an optional **Code** field with the same "leave blank to auto-generate" pattern used for item types.
- Inventory Catalog list / dashboard surfaces the item `code` as a visible column and includes it in search.

## Out of scope

- Migrating inventory item type PK to a code-based scheme — item types keep an integer surrogate PK plus their stable `code` column; only the inventory **item** PK changes here.
- Cross-locale translation editing in the item-type CRUD — only the admin's active locale is editable; other locales come from seed migration or fall back to the canonical name.
- CRUD UI for other inventory taxonomies (units of measure, etc.) — track separately if needed.
- Renaming an inventory item code post-save — codes are immutable once assigned; deactivate + recreate if a code needs to change.
- Storage integration / Order Entry modal lift / Location column — tracked in companion story OGC-657.

## Risks / dependencies

- Any reports, filters, imports, or APIs that currently reference the hard-coded item-type strings or the integer inventory item PK must be updated as part of this story.
- The PK type change touches every module that references inventory items — kickoff should include a quick code-search to enumerate references so none are missed at PR review.
- Coordination with companion storage story OGC-657 if the two ship in the same release: both touch the inventory lot table.

## Definition of Done

- Liquibase release runs cleanly on a fresh database. `inventory_item_type` created with seed + locale data, inventory item PK migrated to string `code`, all FK references updated.
- Inventory item types can be added, renamed (for the active locale), and deactivated via the new admin page.
- The Inventory Catalog → Item Add type dropdown is sourced from the new table. The hard-coded list is gone from source.
- Inventory items can be created with an optional Code (auto-generated when blank); duplicate / malformed codes are rejected with i18n-keyed error copy; the code is locked once saved.
- No hard-coded item-type list remains. No code path retains the legacy integer inventory-item FK.
- Unit and integration tests cover the new admin CRUD, the Item Add dropdown wiring, and code generation + collision handling.
- Release notes document both breaking changes (item-type source of truth, item PK type).

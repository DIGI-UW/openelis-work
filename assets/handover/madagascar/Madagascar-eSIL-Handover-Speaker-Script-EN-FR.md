## Slide 22: Three doors

**EN**

The same message in the wrong place goes nowhere. A bug posted as a general question gets a workaround, not a fix. A feature idea buried in a support thread never reaches the roadmap. So ask yourself, in order: Is something broken? Then it is a bug. Does it work, but you want more? Then it is a feature request. Do you just need to understand something? Then it is a question. These are the same three words we used during the warranty. And if you are not sure, post in Ask OpenELIS. The community will redirect you.

**FR**

Le même message au mauvais endroit n'aboutit pas. Un bogue publié comme question générale obtient un contournement, pas une correction. Une idée de fonctionnalité perdue dans un fil de support n'atteint jamais la feuille de route. Alors posez-vous ces questions, dans l'ordre : quelque chose est cassé ? C'est un bogue. Cela fonctionne, mais vous voulez plus ? C'est une demande de fonctionnalité. Vous voulez simplement comprendre ? C'est une question. Ce sont les mêmes trois mots que pendant la garantie. Et si vous n'êtes pas sûr, publiez dans Ask OpenELIS. La communauté vous redirigera.

## Slide 24: Reporting a bug well

**EN**

Give your Madagascar Distro version and your OpenELIS Global version. Give the steps to reproduce. And attach the exact error message, a screenshot, or the log. The exact wording matters more than a description. A good bug report is fixed faster.

**FR**

Comment bien signaler un bogue. Un bogue par message ; en regrouper plusieurs ralentit tout. Dites ce que vous attendiez et ce qui s'est passé à la place. Indiquez votre version de la Distribution Madagascar et d'OpenELIS Global. Donnez les étapes pour reproduire. Et joignez le message d'erreur exact, une capture d'écran ou le journal. Le texte exact compte plus qu'une description. Un bon signalement est corrigé plus vite.

## Slide 26: Working with your own developers

**EN**

This is the most important slide for sustainability. If the Ministry hires a developer or a company, here is how it works. The developer posts the plan in Development before writing code, so nobody does the same work twice. The developer asks technical questions on the forum, on Slack, and on the Thursday call. The code is submitted as a pull request to the OpenELIS Global repository on GitHub. Community maintainers review it, and that can take several rounds. Once merged, it is in the next release for everyone, and it stays maintained. Please ask your developer to build on the shared product, not on a private copy. A private copy looks faster. After one year it cannot take upgrades and nobody else maintains it.

**FR**

C'est la diapositive la plus importante pour la pérennité. Si le Ministère engage un développeur ou une entreprise, voici comment cela fonctionne. Le développeur publie son plan dans Development avant d'écrire du code, pour que personne ne fasse deux fois le même travail. Il pose ses questions techniques sur le forum, sur Slack et à l'appel du jeudi. Le code est soumis sous forme de pull request sur le dépôt OpenELIS Global sur GitHub. Les mainteneurs de la communauté le relisent, et cela peut prendre plusieurs tours. Une fois fusionné, il est dans la prochaine version pour tout le monde, et il reste maintenu. Demandez à votre développeur de travailler sur le produit partagé, pas sur une copie privée. Une copie privée semble plus rapide. Au bout d'un an, elle ne peut plus recevoir les mises à jour et personne d'autre ne la maintient.

## Slide 33: Fixing translations yourselves

**EN**

All OpenELIS Global screen text is translated in Transifex, and eSIL loads its translations from there. There are two French translations. French, code fr, is the main French shared by every French-speaking country. If a French word is wrong, correct it there, and everyone benefits. French Madagascar, code fr underscore MG, is only for words that are specific to Madagascar. It replaces the main French for eSIL only. Keep that list short. So the rule is: wrong French, fix it in fr. Different in Madagascar, put it in fr_MG. Malagasy can be added later as a new language. To do this, ask for access to the OpenELIS Global project in Transifex, search for the text, and edit it. The change reaches eSIL with the next update.

**FR**

Tous les textes d'écran d'OpenELIS Global sont traduits dans Transifex, et eSIL y charge ses traductions. Il existe deux traductions françaises. Le français, code fr, est le français principal partagé par tous les pays francophones. Si un mot français est faux, corrigez-le là, et tout le monde en profite. ## Slide 35: The upgrade procedure and checklist

**EN**

The full procedure is on the wiki. Here is the checklist before you upgrade production. Read the release notes, especially the upgrade notes and known issues. Check for new settings you must set. Check which of your configurations are affected. Back up the database. Upgrade a test server first, because database migrations cannot be undone. Test the main workflows on the test server. Then upgrade production; migrations run automatically on first start. And tell users what changed. Three things that are good to know: database changes run automatically, existing data is kept and migrated, and old and new screens can exist side by side, so you can adopt new tools at your own pace. If the test server upgrade fails, post in Ask OpenELIS with the log. Do not touch production.

**FR**

La procédure complète est sur le wiki. Voici la liste de contrôle avant de mettre à jour la production. Lisez les notes de version, surtout les notes de mise à jour et les problèmes connus. Vérifiez les nouveaux paramètres à définir. Vérifiez quelles configurations sont touchées. Sauvegardez la base de données. Mettez d'abord à jour un serveur de test, car les migrations de base de données sont irréversibles. Testez les flux principaux sur le serveur de test. Puis mettez à jour la production ; les migrations s'exécutent automatiquement au premier démarrage. Et informez les utilisateurs de ce qui a changé. Trois choses bonnes à savoir : les changements de base de données sont automatiques, les données existantes sont conservées et migrées, et anciens et nouveaux écrans peuvent coexister, donc vous adoptez les nouveaux outils à votre rythme. Si la mise à jour du serveur de test échoue, publiez dans Ask OpenELIS avec le journal. Ne touchez pas à la production.
